# Papercuts

Friction encountered while working in this repo — logged in the moment, none of it blocking. See CLAUDE.md → "Log papercuts".

## 2026-08-10

- (claude-opus-5) Editing the adapter's index.js then rebuilding tests/fixtures/basic-app silently used STALE adapter code: bun's file:../../.. workspace install hardlinks the repo into node_modules/.bun/svelte-kit-bun@root, and editing a file breaks the hardlink so the fixture keeps the old inode. Had to 'rm -rf node_modules/.bun/svelte-kit-bun@root && bun install'. Wasted ~15 min debugging a 'config not passed through' phantom. A pretest step or a note in the fixture README would help.
- (opus-5) Full-suite `bunx vitest run` in svelte-kit-bun intermittently fails with 'bun run build failed (status 1)': tests/executable.spec.ts and tests/kit3-build.spec.ts both run `vite build` in the same fixture dir (tests/fixtures/basic-app) and rm its .svelte-kit, and vitest runs spec files in parallel threads. Fix is probably fileParallelism:false (or per-test out dirs + no shared .svelte-kit wipe).
- (opus-5) svelte-kit-bun: the integration specs all rm -rf the same tests/fixtures/basic-app/.svelte-kit, and vitest runs spec files in parallel by default — adding a third build-based spec made builds clobber each other and fail nondeterministically. Fixed by adding vitest.config.ts with fileParallelism:false; a per-spec fixture copy would be the real fix.
- (opus-5) svelte-kit-bun has a `lint`/`format` script calling `prettier --check .` but no prettier config and no prettier devDependency — so `bunx prettier --write` reformats the whole repo away from its actual style (tabs, single quotes, no trailing commas), and `bunx` also touches bun.lock. Needs a committed .prettierrc + prettier in devDependencies.
- (opus-5) vitest 4: '--reporter=basic' no longer exists and fails with a confusing 'Failed to load custom Reporter from basic' startup error instead of an unknown-reporter message; had to rerun with the default reporter.
- (opus-5) Found an orphaned compiled fixture app (`./build-instr-c/app`, from an ad-hoc build no longer in the tree) still listening on port 5391/5392 half an hour after the run that started it; `start_app`'s `free_port` also hands out surprisingly low ports on macOS, so such orphans collide with hand-picked probe ports. A global teardown that reaps every spawned app would avoid leaving these behind.
